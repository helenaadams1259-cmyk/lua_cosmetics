LuaCosmetics Technical Handbook

Đây là tài liệu tham khảo cho người mới bắt đầu làm việc với dự án LuaCosmetics. Mục tiêu của file này là giúp bạn hiểu cấu trúc hệ thống, nơi đặt logic, cách dữ liệu lưu trữ, cách auth hoạt động, và cách thêm feature mới mà không làm phá hệ thống.

Quan trọng: repo hiện tại chủ yếu là backend, không có frontend riêng trong workspace. Vì vậy phần frontend dưới đây mô tả cách một frontend nên giao tiếp với API này nếu bạn triển khai sau.

1. Project Overview

LuaCosmetics là một API backend cho một cửa hàng mỹ phẩm/cosmetics. Mục tiêu chính là cho phép quản lý:

  • sản phẩm
  • danh mục
  • thương hiệu
  • đơn hàng
  • người dùng
  • quyền admin

Hệ thống được xây bằng FastAPI + SQLite. FastAPI chịu trách nhiệm nhận request HTTP, kiểm tra dữ liệu đầu vào, gọi logic nghiệp vụ, và trả response JSON hoặc CSV. SQLite được dùng như database local để đơn giản hóa phát triển và chạy thử.

Kiến trúc tổng thể

LayerVai tròVí dụ file
HTTP layerNhận request, định nghĩa route, validate cơ bản bằng Pydanticapp/controllers/*.py
Service layerĐóng gói logic nghiệp vụ, kiểm tra điều kiện, orchestrate thao tácapp/services/*.py
Repository layerThực hiện SQL, đọc/ghi dữ liệu, biến đổi kết quảapp/repositories/*.py
Database layerQuản lý kết nối SQLite và schema ban đầuapp/db.py, sql/init_db.sql
Schema layerĐịnh nghĩa request/response shapeapp/schemas/*.py

Đây là một project theo phong cách MVC-ish, nhưng được điều chỉnh cho backend API. Không nên hiểu nó là một framework frontend; nó là một backend service dùng để phục vụ một client khác.

2. Backend Architecture

Khi một request đi vào hệ thống, nó đi qua một số tầng theo thứ tự sau:

graph TD
A[Client] --> B[FastAPI Router]
B --> C[Service]
C --> D[Repository]
D --> E[SQLite Database]
E --> D
D --> C
C --> B
B --> F[HTTP Response]

2.1 Request lifecycle

  1. Client gọi một endpoint như GET /products hoặc POST /admin/products/bulk-csv.
  2. FastAPI nhận request và chọn router phù hợp.
  3. Router đọc các tham số, body, file upload, header và gọi function xử lý.
  4. Nếu cần auth, dependency như Depends(get_current_user) hoặc Depends(require_admin) sẽ chạy trước.
  5. Controller gọi service hoặc repository để xử lý nghiệp vụ.
  6. Repository thực hiện SQL và trả kết quả về.
  7. FastAPI tự động serialize kết quả thành JSON hoặc định dạng khác.

2.2 Router responsibility

Router nằm trong app/controllers. Router không nên chứa SQL trực tiếp và không nên chứa logic phức tạp. Vai trò của router là:

  • định nghĩa endpoint
  • nhận request và validate đầu vào bằng Pydantic
  • gọi service hoặc repository
  • trả response đúng format

Ví dụ: app/controllers/product_controller.py định nghĩa các route cho public products, nhưng không nên tự viết câu SQL. Nếu bạn cần thêm logic filter, hãy cho vào repository hoặc service.

2.3 Service layer

Service là nơi để đặt logic nghiệp vụ. Đây là lớp thích hợp khi bạn cần:

  • kiểm tra dữ liệu trước khi lưu
  • tạo business rules
  • gọi nhiều repository cùng lúc
  • chuyển đổi dữ liệu trước/ sau khi xử lý

Trong repo này, app/services/base_service.py cung cấp CRUD generic cho nhiều entity. Các service riêng như UserService và AuthService có logic càng cụ thể càng tốt.

Rule: nếu logic là “business rule” chứ không phải “database query”, hãy đặt ở service. Nếu logic là “SELECT/INSERT/UPDATE/DELETE”, hãy đặt ở repository.

2.4 Repository layer

Repository là tầng trực tiếp giao tiếp với SQLite. Nó gồm các hàm như:

  • get(), list(), add(), update(), delete()
  • các hàm search/filter đặc thù như filter_products(), search_admin_products()
  • các thao tác transaction cho order

Repository nên tập trung vào SQL và dữ liệu. Nó không nên nhận request HTTP hoặc định nghĩa response. Nếu bạn cần trả một dict có cấu trúc chuẩn, repository vẫn có thể làm điều đó, nhưng không nên “biết” về user-facing response format quá sâu.

2.5 Database layer

Database kết nối được setup trong app/db.py. Khi ứng dụng khởi động, init_db() sẽ chạy sql/init_db.sql để tạo tables nếu chưa tồn tại.

Đây là nơi bạn cần kiểm tra khi dữ liệu bất thường. Nếu một record không hiện lên như mong đợi, hãy nhìn:

  • schema SQL
  • repository query
  • giá trị lưu vào DB

2.6 Model layer

Trong hệ thống này, “model” là sự kết hợp của SQL tables + Pydantic schemas + repository logic. Không có ORM như SQLAlchemy. Vì vậy bạn cần hiểu cả ba phần này để biết một entity được biểu diễn như thế nào.

Ví dụ product có:

  • cột trong bảng products trong SQLite
  • schema trong app/schemas/product_schema.py
  • repository trong app/repositories/product_repository.py

3. Frontend Architecture

Trong workspace hiện tại không có thư mục frontend. Điều này có nghĩa là backend đang được thiết kế để phục vụ một frontend riêng sau này. Nếu bạn thêm frontend, hãy giữ đúng phân tầng sau:

3.1 Frontend responsibilities

  • Routing: điều hướng giữa các trang như danh sách sản phẩm, chi tiết, giỏ hàng, checkout, admin.
  • Pages: mỗi trang chịu trách nhiệm render UI và gọi API.
  • Components: phần tử UI lặp lại như button, card sản phẩm, modal, form.
  • API layer: nơi gom tất cả request HTTP và xử lý response chuẩn.
  • State management: lưu dữ liệu auth, giỏ hàng, user profile, danh sách sản phẩm.
  • UI flow: component fetch data, render, user tương tác, gọi API tiếp.

3.2 Where API calls should live

Logic gọi API nên ở tầng API layer, không nên lẫn vào component. Nếu component đang trực tiếp viết fetch() ở nhiều chỗ, hãy tách thành hàm như productApi.getProducts() hoặc adminApi.bulkImportProducts().

3.3 Where business logic should live

Logic như “nếu user chưa login thì show login modal”, “nếu sản phẩm hết hàng thì disable nút mua”, “tính tổng tiền sau khi giảm giá” nên nằm ở tầng state hoặc service của frontend, chứ không nằm trong component render thô.

3.4 Typical page load flow

  1. Trang mount.
  2. Page gọi API layer.
  3. API layer gọi backend endpoint.
  4. Frontend nhận JSON.
  5. State cập nhật.
  6. Component render UI.

Ví dụ: khi mở trang sản phẩm, frontend nên gọi GET /products/product-filter rồi render danh sách dựa trên kết quả.

4. Authentication System

Auth hiện tại dùng JWT và dependency injection. File chính là app/auth.py.

sequenceDiagram
participant Client
participant FastAPI
participant AuthDependency
participant DB
Client->>FastAPI: Request with Authorization Bearer token
FastAPI->>AuthDependency: get_current_user()
AuthDependency->>AuthDependency: Decode JWT
AuthDependency->>DB: lookup user by username
DB-->>AuthDependency: user row
AuthDependency-->>FastAPI: user dict
FastAPI-->>Client: protected response

4.1 Login flow

  1. Client gửi username/password đến endpoint login.
  2. Backend xác thực mật khẩu bằng bcrypt.
  3. Nếu đúng, server tạo JWT và trả về token.
  4. Client lưu token ở client storage (ví dụ localStorage, memory, hoặc cookie nếu frontend được triển khai).

4.2 How /admin/me works

Endpoint GET /admin/me không đọc user từ một bảng riêng. Nó lấy thông tin user từ token và kiểm tra quyền admin. Nếu token hợp lệ và user là admin, response trả về profile.

Điều này khiến việc “lấy profile hiện tại” không cần một endpoint riêng cho user public.

4.3 Token storage and security

Hiện code backend không làm việc trực tiếp với browser storage. Đây là trách nhiệm của frontend khi triển khai. Một frontend nên:

  • lưu token an toàn
  • gửi token trong header Authorization: Bearer ...
  • xoá token khi 401 hoặc logout

4.4 401 handling and protected routes

Nếu token không hợp lệ hoặc hết hạn, backend trả lỗi 401 Unauthorized. Frontend nên:

  • clear state auth
  • chuyển về màn hình login
  • không tiếp tục gọi API nữa cho đến khi user login lại

Trong repo này, admin routes dùng dependency Depends(require_admin), nên một request không có quyền admin sẽ nhận 403 Forbidden.

5. Database Design

Database hiện tại là SQLite file database.db, schema được tạo bởi sql/init_db.sql. Vì không dùng ORM nên bạn cần đọc SQL schema trực tiếp khi sửa database.

5.2 Product-related tables

5.3 Relationships

  • products.category_id → categories.id
  • products.brand_id → brands.id
  • order_items.order_id → orders.id with ON DELETE CASCADE
  • product_images.product_id → products.id

Điều quan trọng: product và category/brand là mối quan hệ nhiều-1. Một category có nhiều product, một product chỉ thuộc 1 category. Một brand có nhiều product, một product chỉ thuộc 1 brand hoặc không có brand.

5.4 How images are stored

Trong code hiện tại, ProductRepository lưu images dưới dạng JSON string trong cột products.images. Điều này là một design cụ thể của project, nên khi sửa code bạn nên tuân theo nó hoặc có suy nghĩ kỹ trước khi đổi.

Ví dụ dữ liệu lưu trong DB có thể là:

["https://example.com/a.jpg", "https://example.com/b.jpg"]

Nếu bạn cần thay đổi cách lưu ảnh, hãy cập nhật cả parser, repository, schema và frontend cùng lúc.

5.5 Constraints developers must respect

  • products.category_id không được null vì schema dùng NOT NULL.
  • products.slug phải unique.
  • users.username phải unique.
  • orders.status nên dùng các giá trị chuẩn như pending, confirmed, shipping, completed, cancelled.
  • Foreign keys được bật bằng PRAGMA foreign_keys = ON.

6. Product Module

Module sản phẩm là một trong những phần quan trọng nhất của project. Nó đóng vai trò cốt lõi cho storefront và admin management.

6.1 Product CRUD

  • GET /products lấy danh sách sản phẩm công khai.
  • GET /products/slug/{slug} lấy sản phẩm theo slug.
  • GET /products/{slug}/{product_id} lấy sản phẩm theo ID và slug.
  • POST /admin/products tạo sản phẩm mới.
  • PUT /admin/products/{product_id} cập nhật sản phẩm.
  • DELETE /admin/products/{product_id} xóa sản phẩm.

6.2 Search, filters and pagination

Product search hiện tại hỗ trợ:

  • tìm theo q (name hoặc slug)
  • lọc theo khoảng giá
  • lọc theo brand
  • lọc theo category slug
  • phân trang bằng page, page_size

Logic này nằm trong ProductRepository.filter_products() và count_filtered().

6.3 Product images

Ảnh sản phẩm được chuyển đổi trước khi lưu vào DB. Trong repository, list ảnh được encode thành JSON string. Khi đọc lại, repository sẽ decode về list. Nếu bạn thêm trường ảnh mới hoặc thay đổi kiểu lưu, hãy sửa cả encode/decode logic.

6.4 Bulk CSV import

Bulk import là một tính năng quan trọng trong admin. Endpoint:

  • POST /admin/products/bulk-csv để upload file CSV
  • GET /admin/products/bulk-csv/template để download template CSV

Flow thực tế là:

  1. Admin upload CSV.
  2. Backend đọc file bằng csv.DictReader.
  3. Parser validate từng dòng.
  4. Parser kiểm tra category_id và brand_id có tồn tại không.
  5. Nếu hợp lệ, backend tạo product hàng loạt.
  6. Response trả về tổng dòng, số insert thành công, số lỗi.

Đây là một ví dụ tốt về nơi logic “import” nên nằm. Parser và template logic ở app/services/product_import_service.py, route ở app/controllers/admin_controller.py.

6.5 CSV template format

Template CSV sử dụng các cột như:

  • name, slug, category_id, brand_id
  • price, original_price, stock
  • short_description, description, ingredients, usage_instructions
  • image_urls, featured, best_seller, new_product

Nếu bạn đổi cột trong template, hãy đổi parser và test về cùng lúc.

7. Category Module

Category là bộ phận dùng để phân nhóm sản phẩm.

7.1 CRUD

  • POST /admin/categories tạo danh mục
  • GET /admin/categories lấy danh mục cho admin
  • PUT /admin/categories/{id} cập nhật
  • DELETE /admin/categories/{id} xóa

7.2 Relationships

Một category có nhiều product. Nếu xóa category, các product đang tham chiếu category_id có thể vi phạm foreign key. Vì vậy khi thay đổi delete behavior, hãy suy nghĩ kỹ.

7.3 Validation

Category nên có name và slug. Slug cần unique vì repository dùng unique constraint ở DB level. Nếu bạn thêm rule khác như bắt buộc image, hãy thêm ở schema và validation level.

8. Brand Module

Brand biểu thị thương hiệu của sản phẩm.

8.1 CRUD

  • POST /admin/brands
  • GET /admin/brands
  • PUT /admin/brands/{id}
  • DELETE /admin/brands/{id}

8.2 Relationships

Brand và product có mối quan hệ one-to-many. Nếu bạn xóa brand nhưng vẫn còn product dùng brand_id, database có thể lỗi. Hãy xử lý đúng bằng kiểm tra hoặc cập nhật product trước.

8.3 Validation

Brand thường chỉ cần minimum là tên và mô tả. Nếu bạn thêm field như website hoặc logo, hãy cập nhật schema, repository và SQL đồng bộ.

9. API Design Principles

Project này đang dùng REST-style API. Các endpoint nên thống nhất và dễ đoán.

9.1 Naming conventions

  • resource dùng danh từ số nhiều: /products, /categories, /orders
  • admin route dùng prefix /admin
  • action cụ thể dùng path con như /status, /bulk-csv, /me

9.2 HTTP methods

MethodMeaningExample
GETRead/products
POSTCreate/admin/products
PUTUpdate/admin/orders/{id}
DELETERemove/admin/products/{id}

9.3 Response formats

Hầu hết response là JSON object, trong một số endpoint như template CSV thì response là plain text CSV.

Pagination format theo kiểu:

{
  "data": [...],
  "total": 25,
  "maxPage": 3
}

Với các endpoint import, response nên trả về summary rõ ràng:

{
  "total_rows": 10,
  "imported_rows": 8,
  "failed_rows": 2,
  "errors": [...] 
}

9.4 Error formats

Backend hiện tại dùng FastAPI exception và trả về JSON thông thường như:

{"detail": "Admin privileges required"}

Cho import CSV, errors được gom vào list, không nên chỉ throw chung một exception cho cả file. Nếu có nhiều dòng lỗi, hãy trả list lỗi line by line.

9.5 How new endpoints should be implemented

  1. Định nghĩa route trong controller.
  2. Đặt logic nghiệp vụ vào service nếu cần.
  3. Đặt SQL vào repository.
  4. Định nghĩa schema request/response.
  5. Thêm validation.
  6. Test bằng request thật hoặc unit test nếu có thể.

11. Coding Standards

11.1 Naming

  • file names nên nhỏ, rõ ý nghĩa: product_repository.py, auth_service.py
  • function names nên là động từ hoặc câu hỏi rõ ràng: create_order, filter_products, get_current_user
  • biến nên mô tả intent: category_id, product_payload, import_result

11.2 Repositories and services

  • Repository chỉ làm dữ liệu.
  • Service có thể gọi nhiều repository và xử lý logic.
  • Controller chỉ chuyển dữ liệu HTTP.

11.3 Validation

Hãy validate ở nhiều nơi:

  • schema Pydantic cho request
  • service cho business rule
  • repository cho data integrity nếu cần

11.4 Error handling

Không nên expose raw SQL traceback cho người dùng. Nên dùng HTTPException hoặc trả về error summary có cấu trúc rõ ràng. Đối với import CSV, nên trả list lỗi thay vì crash toàn bộ request.

11.5 Database access

Luôn dùng repository hoặc service để thao tác DB. Tránh câu SQL trực tiếp trong controller. Khi thêm cột mới, hãy cập nhật cả SQL schema, repository, schema và test.

12. Adding a New Feature

Khi thêm một feature mới, hãy làm theo quy trình dưới đây để giảm rủi ro.

Ví dụ: thêm entity mới

  1. Bước 1: Xác định entity cần gì và có cần bảng mới không. Nếu có, sửa sql/init_db.sql.
  2. Bước 2: Tạo schema request/response trong app/schemas/.
  3. Bước 3: Tạo hoặc mở repository để thêm CRUD/query.
  4. Bước 4: Nếu cần logic nghiệp vụ, tạo hoặc mở service.
  5. Bước 5: Tạo router trong app/controllers/.
  6. Bước 6: Nếu có frontend, thêm API client và page.
  7. Bước 7: Thêm validation và error handling.
  8. Bước 8: Viết test hoặc ít nhất một manual smoke test.
  9. Bước 9: Cập nhật documentation.
Nếu feature ảnh hưởng đến DB, hãy xem lại foreign keys, unique constraints, và data migration. Đừng giả định dữ liệu cũ sẽ tự chuyển đổi.

13. Common Mistakes

13.1 Bypassing the service layer

Viết logic trực tiếp trong controller là sai vì làm controller trở nên “quá nặng”. Logic nghiệp vụ nên ở service. Nếu bạn cần test logic logic, service dễ test hơn router.

13.2 Writing SQL inside routers

Router không nên biết SQL. Nếu bạn chèn câu SQL trực tiếp vào controller, bạn sẽ khó maintain, khó test, và khó tái sử dụng.

13.3 Calling repositories directly from frontend

Frontend không có quyền gọi repository. Frontend chỉ gọi API HTTP. Nếu bạn viết frontend gọi SQLite trực tiếp, tức là bạn đang làm sai tầng phân chia.

13.4 Breaking response formats

Đổi response structure mà không cập nhật frontend sẽ làm UI lỗi. Nếu cần đổi, hãy thống nhất và cập nhật tất cả consumer.

13.5 Forgetting validation

Không validate input sẽ dẫn tới dữ liệu rác, lỗi cơ sở dữ liệu, và khó debug. Hãy validate ở schema và service.

13.6 Ignoring foreign keys

Thêm product với category_id không tồn tại sẽ bị lỗi nếu không validate đúng. Hãy luôn kiểm tra foreign key trước khi insert.

13.7 Hardcoding URLs

Đừng hardcode http://127.0.0.1:8000 vào nhiều chỗ. Nếu deploy sang môi trường khác, việc này sẽ gây lỗi.

13.8 Mixing UI and business logic

Frontend và backend mỗi bên nên có vai trò riêng. Logic business chính nên ở backend. UI chỉ quyết định cách hiển thị.

14. Debugging Guide

14.1 Backend issues

  • Kiểm tra endpoint trong app/controllers.
  • Xem request có đúng schema không.
  • Kiểm tra service có được gọi không.
  • Kiểm tra repository query.
  • Kiểm tra DB file database.db.

14.2 Authentication failures

  • Xác minh header Authorization: Bearer xxx.
  • Kiểm tra token có đúng secret và algorithm không.
  • Kiểm tra user trong DB còn tồn tại không.
  • Kiểm tra endpoint có dependency admin không.

14.3 CSV import failures

  • Kiểm tra header CSV có đúng tên cột không.
  • Kiểm tra giá trị category_id và brand_id.
  • Kiểm tra các field dạng boolean hoặc numeric.
  • Kiểm tra slug unique.

14.4 API errors and 401/403

401 thường là auth issue. 403 thường là quyền không đủ. 400 thường là input/validation. 404 thường là route hoặc entity không tồn tại. 500 thường là exception chưa được handle đúng.

14.5 CORS and frontend issues

Repo hiện tại không có cấu hình CORS; nếu frontend chạy trên domain khác, bạn cần thêm cấu hình CORS phù hợp. Không nên giả sử browser sẽ tự gọi API thành công nếu backend và frontend ở khác origin.

16. Important Things Every Developer Must Know

  • Never bypass the service layer. Nếu logic cần xử lý, đặt vào service.
  • Always validate user input. Không phụ thuộc vào frontend.
  • Never expose internal SQL errors. Trả về message rõ ràng, không leak stack trace.
  • Keep API responses consistent. Nếu một endpoint trả pagination thì nên giữ cấu trúc thống nhất.
  • Respect database constraints. Slug unique, foreign keys, status values, NOT NULL fields là quan trọng.
  • Do not duplicate business logic. Nếu một rule dùng ở nhiều nơi, hãy đặt ở chỗ chung.
  • Separate frontend and backend responsibilities. Frontend renders; backend stores and validates.
